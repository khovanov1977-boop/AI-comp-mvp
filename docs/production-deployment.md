# Публикация одного сайта на aicomp.fun

Эта конфигурация запускает один общий сайт с открытой регистрацией. Все аккаунты
используют одну базу данных, а API проверяет владельца чатов, персонажей и медиа.
Новая база пустая: локальные аккаунты и файлы не переносятся. Лимиты на аккаунт
остаются 10 изображений, 3 видео, 500 текстовых и 50 голосовых сообщений
персонажей за всё время. Старый черновик `docker-compose.beta.yml` к этой схеме
не относится.

## Перед открытием сайта

1. Нужен Linux VPS с доступом по SSH, установленными Docker Engine и Docker
   Compose, работающим DNS `A` для `aicomp.fun` и доступными входящими портами
   80/443. Порт PostgreSQL наружу не публикуется. Если на VPS уже работает
   сервер на 80/443, сначала согласуйте его настройку вместо запуска второго
   прокси.
2. Для публичного сайта создайте **отдельный** ключ Venice типа Inference Only.
   Установите для него `consumptionLimit.usd = 30` и `limitPeriod = LIFETIME`:
   дневной (`EPOCH`) или месячный (`MONTH`) период со временем обнулит счётчик.
   Если аккаунт использует DIEM или пакетные кредиты, проверьте их отдельные
   ограничения перед запуском. В `.env.production` укажите также общие потолки
   `BETA_MAX_IMAGE_OUTPUTS` и `BETA_MAX_VIDEO_REQUESTS`. Они действуют для
   **всего** сайта дополнительно к лимитам каждого аккаунта. Ноль временно
   запрещает платные генерации
   соответствующего вида.
3. До внешнего запуска разместите политику обработки данных и контакт для
   обращений пользователей. Владельцу сайта нужно проверить актуальные
   требования к обработке персональных данных и передаче данных в Venice.
4. Запланируйте ежедневное резервное копирование базы и тома `app_data` с
   хранением копий вне VPS. Проверяйте восстановление на отдельном стенде.

## Первый запуск на сервере

Разместите репозиторий в отдельном каталоге сервера, например
`/opt/ai-companion`, из проверенного коммита `main`. Создайте секретный файл
из шаблона; заполните его в редакторе непосредственно на сервере и ограничьте
доступ:

```sh
umask 077
cp .env.production.example .env.production
chmod 600 .env.production
```

Для `POSTGRES_PASSWORD` используйте длинную случайную строку **только из букв
и цифр**: она подставляется в URL подключения к БД. `VENICE_API_KEY` также
должен оставаться только на сервере. Не копируйте локальный `.env` и не
помещайте `.env.production` в Git. Перед запуском проверьте, что оба общих
потолка заданы неотрицательными целыми числами.

```sh
docker compose --env-file .env.production -f compose.production.yml config --quiet
docker compose --env-file .env.production -f compose.production.yml up -d --build
docker compose --env-file .env.production -f compose.production.yml ps
docker compose --env-file .env.production -f compose.production.yml logs --tail=100 api web proxy
```

Compose запускает один процесс API. Это важно для фоновых видео-заданий и
учёта общих платных запросов. Caddy выдаёт HTTPS-сертификат и направляет
`/api/*` к API; остальные пути — к Next.js. Прямого доступа к API, сайту и
базе через отдельные публичные порты нет. Секреты не попадают в сборку
браузера: `NEXT_PUBLIC_API_URL` в образе равен `/api`.

## Проверка после запуска

- `https://aicomp.fun` и `https://aicomp.fun/api/health` отвечают без ошибки;
  HTTP перенаправляется на HTTPS.
- Регистрация, выход и повторный вход работают; cookie имеет флаги Secure и
  HttpOnly. Создайте два тестовых аккаунта и проверьте, что персонажи, чаты и
  медиа одного недоступны другому.
- В профиле видны лимиты 10/3/500/50. Проверьте лицо, фигуру, одежду, фото в
  чате, голос и оба сценария видео. Платные операции проводите только после
  проверки общего потолка и баланса Venice.
- Проверьте сайт из российской домашней и мобильной сети. Просмотрите логи API
  на ошибки после каждого сценария.

## Обновление и копии

Перед каждым обновлением создавайте копии PostgreSQL и `app_data`; медиа без
базы или база без медиа не дают полного восстановления. Для резервной копии
можно использовать `pg_dump -Fc` внутри контейнера БД и архивировать том
`ai-companion_app_data`. Храните архивы вне сервера, с ограниченным доступом.
После копии обновляйте код до проверенного коммита и повторяйте `up -d --build`.
Не запускайте одновременно вторую копию API с теми же данными. На новой пустой
базе таблицы создаются при старте; перед будущими изменениями схемы нужна
резервная копия и проверка миграции на отдельном стенде.

Если проверка обновления не прошла, вернитесь к предыдущему коммиту и
пересоберите образы. Если схема базы уже изменилась, потребуется восстановить
согласованную пару копий базы и `app_data`.
